## 1. 문제 — 어느 모드에서 났는지 데이터로 못 가른다

지금 남는 것은 날짜별 두 숫자뿐이다.

```
study_days
┌────────────┬──────────────┬────────────────┐
│ date       │ studiedCount │ memorizedCount │
├────────────┼──────────────┼────────────────┤
│ 2026-08-29 │      30      │       12       │   ← 뭘로 공부했는지는 없다
└────────────┴──────────────┴────────────────┘
```

플래시카드인지 퀴즈인지 예문인지가 **어디에도 없다.** 실제로 두 번 걸렸다:

- **Day 잠금 버그**(`project_plan_day_lock_stuck`) — 제보자가 세 모드 중 어디로 갇혔는지
  못 갈라 재현에 시간을 썼다.
- **예문 모드 학습량 누락** — 새 모드를 만들며 기록 줄을 빠뜨렸는데, 모드별 수치가 없어
  "예문만 0"이라는 사실 자체가 안 보였다. 3번을 고치며 구조는 막았지만
  (`678a136`), *다음에 또 뭔가 빠졌을 때 알아채는 수단*은 여전히 없다.

## 2. 지금 있는 것 — 모드 값은 이미 흐르고 있다

없는 건 값이 아니라 **저장**이다.

```
flashcards/screen.tsx ─┐
quiz/screen.tsx ───────┼─→ finishSession()
examples/screen.tsx ───┘        │
                                ├─→ commitSessionResults(listId, results)   ← 모드를 모른다
                                │      · 암기 전환 · 오답 · 복습 사다리
                                │      · 마지막 학습 시각 · 학습량
                                │
                                └─→ router.replace('/study-results', { mode: 'quiz', … })
                                                                      └── 화면 표시에만 쓰고 버린다
```

세 화면이 결과 화면에 `mode`를 **이미 넘기고 있다**. 그런데 DB 로 가는 길
(`commitSessionResults`)은 그 값을 안 받는다.

🔑 **3번을 먼저 끝낸 덕에 이게 싸졌다.** 커밋 지점이 하나뿐이라, 인자 하나를 늘리면
완주·헤더 백·하드웨어 백 세 경로가 자동으로 따라온다. 예전 구조였다면 기록 지점마다
따로 넣어야 했고, 그게 바로 5번이 필요해진 원인이었다.

## 3. [선택 불필요] — 결정 없이 이렇게 간다

이 넷은 후보를 놓고 고를 것이 없다. 어느 안을 골라도 같다.

1. **모드 값은 `commitSessionResults` 의 인자로 받는다.** 화면이 이미 아는 값이고, 커밋
   지점이 하나라 다른 경로가 생겨도 빠질 수 없다. 전역 상태나 라우터 파라미터를 DB
   레이어에서 읽지 않는다.
2. **낭독(autoplay)은 계속 제외한다.** 통계 제외는 내려진 결정이고, 그 화면은
   `commitSessionResults` 를 아예 안 부른다 — 코드를 손대지 않아도 지켜진다.
   ⚠️ "낭독으로만 공부한 날은 스트릭이 끊긴다"는 별개 논점이다. 이 스펙은 그 결정을
   건드리지 않는다.
3. **소급은 없다.** 지난 기록에는 모드가 없다. 채워 넣을 근거가 없으므로 비운 채 둔다.
   화면에 쓴다면 "이전 기록"으로 묶이거나 도입일 이후만 보여야 한다.
4. **게스트도 같이 남긴다.** 로컬 SQLite 는 게스트도 쓴다. 클라우드로 올릴지는
   §4 의 선택에 달렸고, 로컬 기록 여부는 계정과 무관하다.

## 4. [선택 필요] — 어디에 얼마나 남길 것인가

**먼저 답해야 할 질문 하나:** 이 데이터를 *누가* 볼 것인가?

- **진단용**(내가 본다) — 제보가 왔을 때 모드를 가른다 → **서버에 있어야** 운영 쿼리로 본다.
- **사용자용**(사용자가 본다) — "이번 주 퀴즈 12회" 같은 표시 → **로컬이면 충분**하다.

답에 따라 아래 셋 중 하나다.

### 안 A — 로컬에만, 날짜 × 모드 카운트

```
study_modes  (새 테이블, 로컬 전용)
┌────────────┬────────────┬──────────────┬──────────────┐
│ date       │ mode       │ sessionCount │ studiedCount │
├────────────┼────────────┼──────────────┼──────────────┤
│ 2026-08-29 │ flashcards │      2       │      18      │
│ 2026-08-29 │ quiz       │      1       │      12      │
└────────────┴────────────┴──────────────┴──────────────┘
```

- 크기: 로컬 마이그레이션 **021** 하나 + `commitSessionResults` 인자 하나. 동기화 없음.
- 얻는 것: 사용자에게 보여줄 재료. 기기 안에서만.
- **못 하는 것: 진단.** 제보자 기기의 SQLite 를 볼 방법이 없다 — 5번이 원래 풀려던
  문제를 못 푼다.

### 안 B — 서버까지, `study_days` 에 모드별 칸

```
cloud_study_days  (기존 테이블에 컬럼 추가)
┌────────────┬─────────┬───────────┬──────┬──────────┐
│ date       │ studied │ flashcard │ quiz │ examples │
├────────────┼─────────┼───────────┼──────┼──────────┤
│ 2026-08-29 │   30    │    18     │  12  │    0     │
└────────────┴─────────┴───────────┴──────┴──────────┘
```

- 크기: 로컬 마이그레이션 1 + 서버 마이그레이션 1 + `merge_study_days` RPC 수정 +
  push/pull 매퍼.
- 🔴 **함정이 여기 있다.** `cloud_study_days` 는 기기 간 병합을 **합산이 아니라
  `GREATEST(max)`** 로 한다 — 두 기기가 같은 날 각자 누적한 값을 더하면 이중 계산이라
  일부러 그렇게 정했다(`20260709000000_study_stats_sync.sql`). 모드별 칸을 각각 max 로
  병합하면 **모드 합이 `studied_count` 를 넘을 수 있다.** 화면에 "합계"로 보여주는 순간
  숫자가 안 맞는다. 쓰려면 "각 칸은 최소 하한"이라는 성질을 받아들이거나, 병합 규칙을
  다시 설계해야 한다.
- 🔴 `merge_study_days` 는 **앱이 부르는 RPC** 다. 인자를 바꾸면 구버전 앱이 깨진다 —
  `grant_rewarded_bonus` 때와 같은 유형이다(CLAUDE.md 참조). 새 시그니처를 **덧붙이고**
  옛 것을 남겨야 한다.

### 안 C — 서버까지, 세션 단위 로그

```
cloud_study_sessions  (새 테이블, append-only)
┌──────────────────┬────────────┬────────┬─────────┬───────────┬──────────┐
│ started_at       │ mode       │ seen   │ gotIt   │ list_id   │ plan_day │
├──────────────────┼────────────┼────────┼─────────┼───────────┼──────────┤
│ 2026-08-29 14:02 │ quiz       │   12   │    9    │ …         │    3     │
│ 2026-08-29 14:20 │ flashcards │   18   │   15    │ …         │   null   │
└──────────────────┴────────────┴────────┴─────────┴───────────┴──────────┘
```

- 크기: 로컬 마이그레이션 1 + 서버 테이블 1 + RLS + pull 키셋 인덱스 + push 배선.
  **셋 중 제일 크다.**
- 얻는 것: `memorized_log` 와 같은 append-only 합집합이라 **병합 함정이 없다**(행은
  갱신되지 않고, `ON CONFLICT DO NOTHING`). 진단에 필요한 축(모드·단어장·계획 Day·
  정답률)을 전부 준다 — Day 잠금 같은 제보를 쿼리 하나로 가른다.
- 비용: 행이 세션마다 쌓인다. 사용자 한 명이 하루 5세션이면 연 1,800행 — 지금 규모에서는
  무시할 만하지만 `study_days` 처럼 날짜당 1행이 아니다.
- ⚠️ 개인정보: 무엇을 언제 공부했는지가 서버에 남는다. 이미 `memorized_log` 가 "그날 외운
  단어"를 남기고 있으므로 **새로운 종류의 데이터는 아니다.** 그래도 약관/개인정보 문구가
  이 범위를 덮는지 확인이 필요하다.

### 비교

| | A 로컬만 | B 모드별 칸 | C 세션 로그 |
|---|---|---|---|
| 진단(제보 가르기) | ❌ | △ 날짜 단위 | ✅ 세션 단위 |
| 사용자에게 표시 | ✅ | ✅ | ✅ |
| 병합 함정 | 없음 | 🔴 max 병합 | 없음(append-only) |
| 구버전 앱 위험 | 없음 | 🔴 RPC 시그니처 | 없음(새 테이블) |
| 크기 | 마이그레이션 1 | 로컬1+서버1+RPC | 로컬1+서버1+배선 |

**권고: C.** 5번이 원래 풀려던 문제가 진단이고, B 의 두 🔴 가 실제로 물린 적 있는
유형(`GREATEST` 병합·RPC 시그니처)인 반면 C 는 이미 검증된 `memorized_log` 패턴을
그대로 복제한다. 크기 차이는 B 와 C 가 생각보다 크지 않다 — B 의 RPC 호환 작업이
C 의 새 테이블 작업만큼 든다.

## 5. 착수 전 확인할 것

- [ ] §4 의 질문에 답한다 — 진단용인가, 사용자용인가, 둘 다인가.
- [ ] 안을 고른다.
- [ ] (C 를 고른 경우) 서버에 남는 범위가 현재 개인정보 문구에 들어가는지 확인한다.
- [ ] 화면에 노출할지 결정한다. **노출하지 않기로 해도 5번은 유효하다** — 진단이 목적이면
      화면은 필요 없다.

## 6. 착수하지 않은 이유

1·2·3번과 달리 **이미 있는 배선을 정리하는 일이 아니라 데이터를 새로 모으는 일**이다.
스키마가 걸려 있어 "고치는 김에" 얹을 크기가 아니고, §4 의 질문에 답하지 않으면 셋 중
어느 것도 고를 수 없다. 배포를 미룰 이유는 아니므로 1·2·3번만 먼저 내보낸다.
