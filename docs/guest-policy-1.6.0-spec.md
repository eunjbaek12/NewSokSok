# 게스트 정책 개편 — 1.6.0 스펙

작성 2026-08-16. **결정된 것과 결정이 남은 것을 분리해 적는다.** 착수 전 §7 을 먼저 볼 것.

## 1. 결론

게스트 모드를 **없애지 않는다.** 대신 **게스트라는 등급 자체를 없애고** 로그인 사용자와 완전히
같은 한도를 준다. 로그인의 의미는 한도가 아니라 **백업(클라우드 보관)** 하나로 남는다.

> **왜 로그인을 유도하지 않는가.** 현재 유일한 실수익인 광고는 **게스트도 똑같이 본다**. 구독은
> 로그인만 가능하지만 구독자가 1명이다. 즉 "가입시켜야 돈이 된다"는 지금 사실이 아니다. 로그인의
> 실질 이득은 ①측정 ②유실 리뷰 방지 ③재획득인데, 셋 다 **사용자가 스스로 로그인할 때** 얻어지고
> 억지로 끌어온 계정에서는 오히려 덜 얻어진다. 그래서 기능 제한이 아니라 **안내**로 간다.

근거 세 줄:

- 설치 143 대 가입 77(전환 54%) — 게스트로 남는 사람은 **월 12명 상한**. 지우든 두든 규모가 작아
  데이터로는 갈리지 않는다.
- 게스트 사용을 막아서 얻는 가입보다, **잃는 사용자와 유실 리뷰 리스크**가 비대칭적으로 크다.
- 구독자가 1명이라 구독 전환을 지키려고 사용을 막을 이유가 약하다. **광고는 게스트도 본다.**

## 2. 원칙 — 앱 먼저, 서버 나중

한도(서버 값)는 한 줄이면 바뀌지만 **혼자 바뀌면 안 된다.**

| 이유 | 내용 |
|---|---|
| 남용 | 한도를 올리면 **로그아웃-재진입 리셋**의 1회 이득이 20단어 → **300단어**가 된다 (§3 ①) |
| 정합성 | "게스트 10단어"가 **스토어 원고 10곳 + 앱 문구**에 적혀 있다 (§3 ②③) |

2026-08-13 에 서버를 먼저 바꿔 출시 앱의 보상형 광고가 이틀간 무효가 된 사고와 같은 구조다.
**①②③이 스토어에 도달한 뒤 ④를 적용한다.**

## 3. 단계별 스펙

### ① 익명 세션 유지 — 재생성 차단 【선결 · 선택 불필요】

**문제.** 게스트가 로그아웃하면 익명 세션이 지워지고, 재진입 시 새 계정이 생겨 **AI 한도가 0에서
다시 시작**한다. 로컬 단어는 남으므로 사용자가 잃는 것이 없어 "다시 시작하기"로 보인다.

실측(8/13 새벽, 한 기기): `01:40` 계정이 한도 10 소진 → 광고 1회(게스트 상한) → 보너스 10 →
**20 소진 후 막힘** → `01:52` 새 계정에서 **10을 또 사용**. 12분에 30단어 = 한도의 3배.

한도 10은 사진 스캔 한 장이면 소진되므로 **정상 사용자가 자연히 이 경로에 도달한다.**

**변경.**

| 파일 | 지점 | 내용 |
|---|---|---|
| `features/auth/store.ts` | `logout()` 끝 (현 :453) | 게스트였다면 `supabase.auth.signOut` 을 **호출하지 않는다**. 클라우드 로그인일 때만 유지 |
| `features/auth/store.ts` | `hydrate()` else 분기 (현 :205~212) | 의도가 `none` 이어도 **익명 세션은 고아로 보지 않는다** — 지금은 여기서 지워져 다음 콜드 스타트에 리셋된다 |

두 곳을 함께 고쳐야 한다. 하나만 고치면 앱 재시작 시점에 리셋이 되살아난다.

**주의.** 이 코드는 게스트 진입 크래시(`922b457`)를 고친 자리 바로 옆이다. 그 회귀 테스트
(`__tests__/auth-logout-late-clobber.test.ts`)를 먼저 읽고, 늦게 끝난 `logout()` 이 갓 만든 세션을
덮지 않는 가드를 깨지 않는지 확인할 것.

**남는 우회로.** 앱 재설치 — 로컬 단어 전량 손실이 대가이므로 실질적 억제가 된다. 막지 않되
주 1회 관측한다(§5-2). **①의 가치가 여기에 있다**: 3탭·손실 0 인 싼 경로를 막으면, 남는 것은
단어장을 통째로 버려야 하는 비싼 경로뿐이다.

### ② 앱 문구 — 가입 유인을 백업으로 【확정】

로케일은 **ko · en · es 세 개**(`i18n/locales/`).

**반드시 고쳐야 하는 것.** `plans.currentGuestDesc` — `app/plans.tsx:180`, 게스트가 보는 유일한
로그인 동선이다.

```
현재 (ko)  "Google로 로그인하면 매일 50단어 AI 한도를 무료로 받을 수 있어요."
           → 게스트도 50이 되는 순간 이 문장은 거짓이 된다
```

**확정 문구** — 현재 상태를 먼저 알리고 이득을 붙이는 순서. 위험을 앞세우는 안("앱을 지우면
사라져요")은 첫인상이 무거워 채택하지 않았다.

```
ko  지금 단어장은 이 기기에만 있어요.
    로그인하면 클라우드에 백업되고 다른 기기에서도 이어서 볼 수 있어요

en  Your words live only on this device.
    Sign in to back them up and continue on any device.

es  Tus palabras solo están en este dispositivo.
    Inicia sesión para respaldarlas y seguir en cualquier dispositivo.
```

⚠️ es 는 **tú 형태**로 쓴다(`usted` 금지 — 앱 전체 통일). AI 는 es 에서 **IA**.

**고치지 않는 것.**

- `whatsNew.v150_5`("게스트로 사용하면 10단어") — **이미 나간 과거 소식**이라 손대지 않는다.
  1.6.0 소식에 새 문장을 넣어 갱신한다.
- FAQ 대부분 — "게스트와 Free 는 다음 날 초기화", "게스트와 Free 는 보상형 광고로 한도 추가"처럼
  **수치가 없는 병기 표현**이라 한도가 같아져도 그대로 참이다.
- FAQ "게스트 모드와 로그인의 차이" — 백업 차이를 설명하는 문항이라 오히려 새 포지션과 맞는다.

### ④ 서버 — 게스트 등급을 없앤다 【확정】

대상은 `ai_effective_plan` 한 함수. 새 마이그레이션으로 `create or replace`.

**게스트를 Free 와 같게 하는 데 그치지 않고, `is_anonymous` 분기 자체를 제거한다.**

```sql
-- 지금
tier      : is_anonymous → 'guest', else 'free'
day_limit : pro 3000
          / not is_anonymous and created_at > now()-'24h' → 300
          / is_anonymous → 10
          / else 50
reward_amount    : is_anonymous 10 / else 20
reward_max_views : is_anonymous  1 / else  2

-- 1.6.0 — is_anonymous 가 한 번도 등장하지 않는다
tier      : 'pro' / 'free'
day_limit : pro 3000 / created_at > now()-'24h' → 300 / else 50
reward_amount    : 20
reward_max_views : 2
```

최종 정책은 한 문장으로 적힌다.

```
누구나  첫 24시간 300단어 → 이후 하루 50단어 (+ 광고 1회 20단어, 하루 2회까지 = 최대 90)
Pro     월 3,000단어
게스트 ↔ Free 차이 : 없음.  로그인의 의미 : 백업 · 동기화 · 기기 이동
```

**첫 24시간 300 도 게스트에게 동일하게 준다.** 실측 근거: 300 부스트 도입 후 가입 36명 중
첫날 AI 를 쓴 사람은 10명이고, 그중 **50단어를 넘긴 사람은 1명(575단어)** 이다. 90%에게는
하루 90으로 충분하고, **첫날 대량으로 쓰려는 10% 를 놓치지 않기 위해** 300 을 남긴다.
(원래 근거였던 "첫 세션 사진 스캔이 벽에 부딪힌다"는 하루 90 으로 대부분 해소되므로 약해졌다.)

**앱 영향.** `tier` 에 `'guest'` 가 오지 않으므로 게스트도 요금제 화면에 **Free** 로 표시된다.
광고 가드는 `tier === 'pro'` 만 보므로 영향 없다(`lib/ads/admob.ts`). `tierGuest`·`accountTierGuest`
같은 키는 쓰이지 않게 되면 정리한다. 내부 분석은 `auth.users.is_anonymous` 로 계속 가능하다.

**재설치 우회는 의도적으로 허용한다.** 앱을 지웠다 깔면 새 익명 계정이라 300 을 다시 받는다.
막지 않는 이유:

- 얻는 것이 **1회 약 120원어치**(AI 단어 1개 원가 ≈ 0.4원)인데, 대가는 **쌓아 둔 단어장 전체**다.
- 확실히 막으려면 기기 식별이 필요하고, 그 개발 비용이 남용 손해보다 압도적으로 크다.
- ①로 **로그아웃-재진입(3탭·손실 0)** 을 막고 나면 남는 경로는 재설치뿐이다. 대가가 큰 경로만 남는다.

대신 **관측은 한다** → §5-2.

**적용 조건: ①②③이 스토어에 도달한 뒤.** 앱 릴리스 전에 올리면 문서와 실제가 어긋난다.
**되돌리기**: 서버 값이라 즉시 가능.

### ⑤ 미사용 익명 계정 정리 — 【채택하지 않음】

Supabase 는 익명 계정의 주기적 삭제를 권장하지만 **이번에 하지 않는다.**

전제 정리 — 게스트 데이터는 두 곳에 나뉘어 있다. **단어는 기기에만 있고**(로컬 SQLite, 우리가
접근할 수 없다), 서버에는 **신원 행(`auth.users`)과 사용량 기록(`ai_usage_daily`)** 만 있다.
따라서 "정리"는 단어를 지우는 것이 아니라 서버의 빈 신원 행을 청소하는 뜻이다.

**하지 않는 이유:**

1. 🔴 **①과 충돌한다.** 서버 계정을 지우면 그 기기의 게스트는 다음 실행에서 세션이 무효가 되어
   새 계정을 만든다 → **한도가 리셋된다.** ①로 막으려던 것을 청소가 되살린다.
2. 규모상 불필요하다 — 계정 행은 매우 작고, Supabase 무료 한도는 월 50,000명인데 우리는 월 수십 명이다.
3. 지표 혼동은 `is_anonymous` 로 갈라 보면 해결된다.

⏭️ 익명 계정이 수천 단위로 쌓이면 그때 다시 검토한다. 그때도 **①을 깨지 않는 기준**(예: 세션
만료가 이미 지난 계정만)이어야 한다.

## 4. 표준 대비 — 따르지 않기로 한 것

Supabase 공식 문서와 대조한 결과, **두 가지는 의도적으로 채택하지 않는다.**

| 항목 | 공식 권장 | 채택 여부 |
|---|---|---|
| 익명→영구 계정 **링크 승격** | `updateUser`/identity 링크로 같은 `user_id` 유지 | **안 함.** 링크의 이점은 서버 데이터 이관인데 우리 게스트 데이터는 로컬이라 이관할 것이 없다. 충돌 분기만 늘어난다 |
| **captcha** | 익명 로그인 남용 방지 | **안 함.** 봇의 대량 생성을 막는 장치라, 사람이 3탭으로 리셋하는 경로를 못 막는다. 정당한 게스트에게만 마찰이 생긴다 |
| 익명 계정 정리 | 권장 | **안 함.** ①(세션 유지)과 충돌해 한도 리셋을 되살린다. 규모상 이득도 없다 → ⑤ |

## 5. 검증과 관측

### 5-1. 배포 검증

| 단계 | 방법 |
|---|---|
| ① | 실기: 게스트 진입 → AI 사용 → **로그아웃 → 재진입** → 한도가 이어지는지. 동시에 DB 에서 익명 계정이 늘지 않았는지 확인 |
| ① 회귀 | 게스트 진입 크래시 재현 시나리오(로그아웃 직후 "바로 시작하기" 즉시 탭) |
| ④ | 배포 후 `select * from ai_effective_plan('<익명 uuid>')` — `tier='free'`·`day_limit` 300/50 확인 |

### 5-2. 재설치 남용 관측 — 막지 않되 눈은 뜬다

**남용은 서버에 특징적인 흔적을 남긴다.**

```
정상 계정 : 생성 → 조금씩 사용 → 며칠에 걸쳐 활동이 이어짐
남용 계정 : 생성 → 24시간 내 300 소진 → 이후 활동 0 → 곧 새 계정 등장
```

8/13 데이터에서 실제로 관측된 모양이다(`01:40` 소진 → `01:52` 새 계정). 로그아웃 경로였지만
재설치도 같은 형태로 남는다. 여기에 `auth.sessions` 의 **IP 대역 + user_agent** 를 얹으면
정밀도가 오른다(어제 익명 14개를 운영자/실사용자로 가른 방법).

**점검**: 주 1회 수동 쿼리. 24시간 내 250단어 이상 소진 + 이후 활동 0 인 익명 계정을
IP /16 대역으로 묶어 센다. → `docs/ops-analytics-queries.md` Q12 로 추가할 것.

**대응 단계**

| 단계 | 관측 | 대응 | 비용 |
|---|---|---|---|
| 0 | 없음 | 그대로 | 0 |
| 1 | 한 대역에서 2~3건 | **300 부스트 축소·폐지**(서버 값) — 표적 자체가 사라진다 | 즉시·0 |
| 2 | 계속·확산 | 기기 식별 도입 | 아래 |

**2단계의 실제 비용**(참고 — DeviceCheck 는 과하다):

| 플랫폼 | 수단 | 재설치 후 유지 | 비용 |
|---|---|---|---|
| Android | `ANDROID_ID`(`expo-application`) | ✅ 거의 확실 | 패키지 1개 |
| iOS | **Keychain 플래그**(`expo-secure-store`, **이미 설치됨**) | △ 대체로 유지, 기기 초기화 시 소실 | 코드 몇 줄 |

서버에 기기 해시 테이블 하나가 추가된다. iOS DeviceCheck(완벽하지만 네이티브 모듈 필요)는
"120원 아끼려고 기기를 초기화하는 사람"까지 막게 되므로 채택하지 않는다.
