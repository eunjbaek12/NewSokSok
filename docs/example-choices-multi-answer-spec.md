# 예문 학습 다중정답 방지 — 스펙

작성 2026-08-20. 상태: **구현 완료 · 미커밋 · 실기 미검증**(2026-08-21). 결과는 11장.

예문 빈칸 문제에서 오답 선택지가 빈칸에 들어가도 문장이 성립해, 화면상 맞는 답을
골라도 오답 처리되는 문제를 고친다. 선택지 생성기만 바꾼다 — **덱 데이터도, 서버도
건드리지 않는다.**

---

## 1. 제보와 재현

문의하기로 받은 제보(2026-08-20 확인):

> TOPIK I Essentials 350 덱 3일차 예문(Examples)에서 `__먹을까요?` 문제가 나왔는데
> 선택지에 **"라면"과 "국수"가 둘 다 있었다.** 논리적으로 둘 다 맞다. 두 단어가 같이
> 안 뜨게 하거나, 둘 다 정답으로 인정되게 해 달라.

서버 데이터(`official_words`)에서 그대로 재현된다:

```
국수 → "국수 먹을까요?"                                  ← 빈칸 뚫으면 "___ 먹을까요?"
라면 → "① 어머니께서 직접 만들어 주신 라면은 언제나 맛있었다.
        ② 저녁으로 라면을 먹을까 합니다."                  ← 빈칸에 넣어도 성립
```

채점은 `word.id` 비교(`features/study/examples/screen.tsx:347`)이므로 "라면"을 고르면
오답이 된다.

## 2. 원인

`features/study/choices.ts`의 `buildChoices`가 오답에서 거르는 것은 셋뿐이다.

1. 정답과 같은 `id`
2. **화면에 표시되는 라벨이 같은 것**
3. 빈 라벨

즉 **"표시가 다른가"만 본다. 봐야 하는 것은 "빈칸에 넣으면 틀리는가"다.**

> 2026-07-26 의 `15a7af4` 는 *표기·뜻이 글자 그대로 중복*되던 별개 버그였다. 이번 건은
> 글자는 다른데 의미상 둘 다 맞는 경우라 그 필터에 걸리지 않는다.

## 3. 실측 (2026-08-20, 서버 `official_words` 15,542행 / 65덱 전수)

### 3.1 덱 재생성으로 얼마나 좋아졌나 — 전체는 좋아졌으나 이 덱은 아니다

| | 번들 (`constants/curationData.ts`) | 서버 (현재) |
|---|---|---|
| 예문이 바뀐 비율 | — | 32.8% (5,103개, 대부분 ①②③ 병기) |
| **문형 겹침** (ja/zh 출발 덱 제외, 9,782문항) | 25.1% | **1.9% (185개)** |
| ↳ TOPIK I Essentials 350 | 27.1% (77개) | **23.8% (69개)** |

TOPIK I 은 병기 교체율이 **16.6%** 밖에 안 된다(다른 덱은 43~57%). 초급 단어라 뜻이
하나뿐이라 병기 대상이 아니었고, 그래서 예문이 옛날 그대로 남았다.

"문형 겹침" = 예문에서 표제어를 뺀 나머지가 같은 덱 안에서 완전히 동일한 문항.
= **확정 다중정답.** 예:

```
"___ 주세요."     ← 영수증 / 환불 / 메뉴 / 비빔밥 / 숟가락 / 입장권 / 왕복
"___ 어디예요?"   ← 국적 / 지하철 / 우체국 / 사무실 / 화장실
"___ 없어요."     ← 지갑 / 우산 / 교통카드 / 회원증 / 휴지
"___ 맛있어요."   ← 국 / 불고기 / 생선
```

### 3.2 덱은 주제 블록으로 정렬돼 있다 — 이게 필터 B의 근거다

TOPIK I 350, position 55~90:

```
55구경하다 56손수건 57반지 58목걸이 59시계 60안경 61우산 │ 62메뉴 63주문하다 64예약하다
65반찬 66국 67찌개 68국수 69라면 70비빔밥 71불고기 72삼겹살 73치킨 74피자 75햄버거
76샐러드 77채소 78생선 79계란 80두부 81김치 82된장 83고추장 84간장 85설탕 86후추 87기름 │ 88맵다 89짜다 90싱겁다
                          └───────────── 62~87 전부 음식 (26개) ─────────────┘
```

TOPIK II 도 같다(경제 블록이 통째로 붙어 있음). **"주제가 같은가"를 AI 에게 물을 필요가
없다 — 덱 내 순서가 이미 답을 갖고 있다.** 국수(68)와 라면(69)은 거리 1이다.

### 3.3 그러나 순서만으로는 부족하다 — 두 필터는 서로 다른 것을 잡는다

문형이 같은 단어 쌍 205개 중 **덱 내 거리 20 이하는 32.2%뿐, 중앙값 거리는 54.**
("___ 주세요"의 영수증·비빔밥·입장권은 서로 멀리 있다.) 그래서 A 와 B 를 **둘 다** 넣는다.

## 4. 기각한 대안

| 안 | 기각 이유 |
|---|---|
| **제보자 제안 (b) "둘 다 정답 인정"** | 라면도 정답으로 처리하면 그 문항은 **아무것도 검증하지 못한다** — "국수"를 몰라도 맞힌다. 변별력이 0 이 된다. 게다가 "무엇까지 허용할지"를 데이터로 들고 있어야 해서 AI 판정 비용이 (a)보다 크다. |
| **예문을 길게 다시 만든다** | 덱 설명이 *"Every example is written within beginner grammar so you can read the whole sentence"* 다. 문맥이 얇은 것은 **이 덱의 의도**다. TOPIK I 학습자에게 "① 어머니께서 직접 만들어 주신 라면은…"을 주는 것은 퇴행이다. |
| **AI 로 의미 그룹 태그 부여** | 비용은 문제가 아니다(15,542단어 태깅 ≈ ₩100~300). 문제는 **얻는 것이 적다**는 점 — 덱이 주제 정렬돼 있는 이상 태그는 순서가 이미 하는 일을 반복하고, 추가로 잡는 것은 "멀리 떨어져 있는데 의미가 겹치는 단어"뿐이다. 대가로 15,542행 재시딩과 검수가 붙고, 태그 입도를 잘못 잡으면(전부 "음식") 오답 후보가 말라 문제가 더 쉬워진다. **A+B 로 부족한 것이 확인되면 그때 추가한다** — 두 필터는 태그가 생겨도 그대로 살아남는다. |
| **문맥이 얇은 예문은 출제 제외** | TOPIK I 은 94%가 2어절 이하라 출제량이 붕괴한다. |

## 5. 설계

### 5.1 호출부가 컨텍스트를 넘긴다 (퇴행 방지)

```
지금
  buildChoices(pool, answer, labelOf, count)

제안
  buildChoices(pool, answer, labelOf, count, ctx?)
                                            └── 선택적 인자
  ctx = { frameOf: (w) => string | null,     // 필터 A
          indexOf: (w) => number,            // 필터 B
          minDistance: number }

  예문 화면 → ctx 넘김 (A+B 작동)
  퀴즈 화면 → 안 넘김 (한 줄도 안 바뀐다)
```

### 5.2 3단계 폴백 — 작은 단어장 보호

```
오답 후보
  ├ 1차  id 중복 · 라벨 중복 · 빈 라벨 제외        ← 항상 (현행)
  ├ 2차  문형이 정답과 같은 것 제외          (A)
  └ 3차  인덱스 거리 20 이내 제외            (B)
  │
  └→ 오답 3개 확보?
        NO → B 해제하고 재시도          ← B 가 더 근사적이므로 먼저 푼다
        NO → A 해제하고 재시도          ← 현행 동작으로 복귀
        NO → 있는 만큼만 (현행과 동일)
```

단어 5개짜리 단어장도 선택지 수가 줄지 않는다.

### 5.3 필터 A — 문형 일치

- 문형 = `segmentExample`(`lib/example-blank.ts`)의 세그먼트 중 **빈칸이 아닌 부분만**
  이어붙인 문자열
- 정규화는 공백 collapse + trim 만. **구두점은 남긴다**(다르면 다른 문장이다)
- 예문이 없거나 `segmentExample`이 null 인 후보는 배제하지 않는다
- 리스트당 1회 계산해 `Map<wordId, frame>` 으로 캐시(`useMemo`, 리스트 id 기준)

🔑 **기존 `segmentExample` 을 재사용하는 것이 핵심이다.** 3장의 측정은 어절 쪼개기라
일본어·중국어 덱을 못 쟀지만, `segmentExample` 은 CJK 범위를 알아내므로 **ja/zh 덱까지
자동으로 커버된다.**

### 5.4 필터 B — 주제 블록 근접

```
정답 인덱스 68 → 배제 구간 [48, 88]
```

🔴 **기준은 `position` 컬럼이 아니라 `selectWordsForList` 가 돌려준 배열의 인덱스다.**

`features/vocab/db.ts:219` 의 `createCuratedList` 는 words INSERT 에 **position 을 아예
넣지 않는다.** createdAt 은 350개가 전부 같은 `now` 다. 그런데 조회는:

```sql
-- features/vocab/db.ts:386
SELECT * FROM words WHERE listId = ? AND deletedAt IS NULL
ORDER BY position ASC, createdAt DESC;
--       └ 전부 NULL      └ 전부 동일  → 타이 브레이커가 없다
```

실무적으로는 rowid(=삽입 순서=덱 순서)로 나오지만 **보장이 없다.** 배열 인덱스는 null
이든 뭐든 항상 존재하고, 사용자가 실제로 보는 순서와 일치한다. (position 컬럼을 채우도록
고치는 것은 별건 — 이미 담긴 단어장은 어차피 NULL 이라 인덱스 기반이면 우회된다.)

## 6. 결정된 파라미터 (2026-08-20)

| 항목 | 결정 | 근거 |
|---|---|---|
| **거리 N** | **±20** | 350개 기준 최대 40개(11%) 배제 → 후보 349→309, 난이도 체감 0. 제보 사례(거리 1)와 음식 블록 중심부를 잡는다. ±35 는 "된장(82)과 김치(81)를 구별하는 문제"까지 못 내게 만들어 과하다. ±10 은 같은 블록의 절반을 놓친다. |
| **`__custom__`(골라서 학습) 경계** | **그냥 둔다** | `selectWordsForList('__custom__')` 는 여러 리스트를 flatMap 하므로 리스트 A 의 끝과 B 의 시작이 "인접"으로 잡힌다. 잘못 배제해도 후보가 몇 개 줄 뿐 문제가 깨지지 않는다. 경계를 인식하려면 `indexOf` 에 listId 를 섞어야 하는데 값어치가 없다. |

## 7. 범위 밖

- **퀴즈 화면.** 뜻↔표기 1:1 이라 다중정답이 나오려면 뜻이 같아야 하는데, 그것은 기존
  라벨 중복 필터가 이미 잡는다. "국=soup / 찌개=stew" 같은 유사 뜻은 남지만 그것은
  다중정답이 아니라 난이도이고, 오히려 구별하는 것이 학습이다.
- **덱 데이터 · 서버.** 재시딩 없음, 마이그레이션 없음. 앱 재빌드만 필요하다.
- **AI 태그.** 4장 참조.
- **`createCuratedList` 의 position 누락.** 5.4 참조 — 별건.
- 🔴 **병기 예문의 빈칸 문제 — 별건으로 분리(2026-08-20 결정).**
  서버 예문의 **32.8%가 ①②③ 병기**로 바뀌었는데, `segmentExample` 은 표제어가 나오는
  **자리마다 전부 빈칸을 뚫는다**(`lib/example-blank.ts:44` — ranges 가 복수). 즉
  "① … 라면은 … ② … 라면을 …" 예문은 **한 카드에 문장 3개 + 빈칸 2~3개**가 된다.
  최장 예문이 229자인 덱도 있다(수능 필수 어휘 500, 병기 57%). 카드 세로 여유는 예전
  실측에서도 빠듯했다. **실기 미확인.**

위험 후보가 2개여도 노출 확률이 1% 안팎). 3장의 "185개"는 *겹치는 문항 수*이고 이쪽은
*실제로 화면에 뜰 기대 횟수*다 — 같은 것을 세지 않는다.

**필터 B (주제 블록 근접)** — 오답에 거리 20 이내 단어가 섞인 문항 비율, 덱 30단어 이상

| 덱 | 필터 전 | 필터 후 |
|---|---|---|
| **TOPIK I Essentials 350** (제보가 온 덱) | 28.4% | **0.0%** |
| 전체 평균 | 68.4% | 23.2% |
| 30단어짜리 주제 덱(입원 및 진단 과정 등) | 100% | ~50% |

🔑 **30단어 덱이 절반만 걸러지는 것은 설계대로다.** 덱 전체가 한 주제라("입원 및 진단
과정") 주제가 다른 오답이라는 게 존재하지 않는다. 폴백이 B 를 풀어 선택지 4개를 지킨 것이고,
그러지 않으면 선택지가 1~2개로 줄어든다.

🔴 **제보 사례(국수/라면)의 제거는 이 표의 B 쪽에서만 확인된다.** 두 단어는 문형이 달라
(`먹을까요?` vs `을 좋아해요.`) A 로는 잡히지 않으며, "빈칸에 넣어도 말이 되는가"는
기계적으로 셀 수 없어 **필터 B 가 없앤 양을 정확히 수치화할 방법은 없다.** 위 28.4% → 0.0%
는 "같은 주제 블록 단어가 오답으로 뜬 빈도"이고, 제보 사례는 그 안에 포함된다.

### 남은 것

- 🔴 **실기 검증**(10장 2번). 특히 `ORDER BY position ASC` 의 타이 없음이 실제로 덱 순서를
  유지하는지 — 필터 B 의 유일한 전제다.
- 커밋. 워킹 트리에 다른 세션 작업이 섞여 있어 경로를 지정해 올려야 한다.
