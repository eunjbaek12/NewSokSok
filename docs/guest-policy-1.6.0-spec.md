# 게스트 정책 개편 — 1.6.0 스펙

작성 2026-08-16 · 갱신 2026-08-17(§3 ②-b 추가).
**결정된 것과 결정이 남은 것을 분리해 적는다.** 착수 전 §7 을 먼저 볼 것.

## 1. 결론

게스트 모드를 **없애지 않는다.** 대신 **게스트라는 등급 자체를 없애고** 로그인 사용자와 완전히
같은 한도를 준다. 로그인의 의미는 한도가 아니라 **백업(클라우드 보관)** 하나로 남는다.

> **왜 로그인을 유도하지 않는가.** 현재 유일한 실수익인 광고는 **게스트도 똑같이 본다**. 구독은
> 로그인만 가능하지만 구독자가 1명이다. 즉 "가입시켜야 돈이 된다"는 지금 사실이 아니다. 로그인의
> 실질 이득은 ①측정 ②유실 리뷰 방지 ③재획득인데, 셋 다 **사용자가 스스로 로그인할 때** 얻어지고
> 억지로 끌어온 계정에서는 오히려 덜 얻어진다. 그래서 기능 제한이 아니라 **안내**로 간다.

근거 세 줄:

- 설치 143 대 가입 77(전환 54%) — 게스트로 남는 사람은 **월 12명 상한**. 지우든 두든 규모가 작아
  데이터로는 갈리지 않는다.
- 게스트 사용을 막아서 얻는 가입보다, **잃는 사용자와 유실 리뷰 리스크**가 비대칭적으로 크다.
- 구독자가 1명이라 구독 전환을 지키려고 사용을 막을 이유가 약하다. **광고는 게스트도 본다.**

## 3. 단계별 스펙

### ① 익명 세션 유지 — 재생성 차단 【선결 · 선택 불필요】

**문제.** 게스트가 로그아웃하면 익명 세션이 지워지고, 재진입 시 새 계정이 생겨 **AI 한도가 0에서
다시 시작**한다. 로컬 단어는 남으므로 사용자가 잃는 것이 없어 "다시 시작하기"로 보인다.

실측(8/13 새벽, 한 기기): `01:40` 계정이 한도 10 소진 → 광고 1회(게스트 상한) → 보너스 10 →
**20 소진 후 막힘** → `01:52` 새 계정에서 **10을 또 사용**. 12분에 30단어 = 한도의 3배.

한도 10은 사진 스캔 한 장이면 소진되므로 **정상 사용자가 자연히 이 경로에 도달한다.**

**변경.**

| 파일 | 지점 | 내용 |
|---|---|---|
| `features/auth/store.ts` | `logout()` 끝 (현 :453) | 게스트였다면 `supabase.auth.signOut` 을 **호출하지 않는다**. 클라우드 로그인일 때만 유지 |
| `features/auth/store.ts` | `hydrate()` else 분기 (현 :205~212) | 의도가 `none` 이어도 **익명 세션은 고아로 보지 않는다** — 지금은 여기서 지워져 다음 콜드 스타트에 리셋된다 |

두 곳을 함께 고쳐야 한다. 하나만 고치면 앱 재시작 시점에 리셋이 되살아난다.

**주의.** 이 코드는 게스트 진입 크래시(`922b457`)를 고친 자리 바로 옆이다. 그 회귀 테스트
(`__tests__/auth-logout-late-clobber.test.ts`)를 먼저 읽고, 늦게 끝난 `logout()` 이 갓 만든 세션을
덮지 않는 가드를 깨지 않는지 확인할 것.

**남는 우회로.** 앱 재설치 — 로컬 단어 전량 손실이 대가이므로 실질적 억제가 된다. 막지 않되
주 1회 관측한다(§5-2). **①의 가치가 여기에 있다**: 3탭·손실 0 인 싼 경로를 막으면, 남는 것은
단어장을 통째로 버려야 하는 비싼 경로뿐이다.

> 🔴 **바로 위 문장은 틀렸다 — 세 번째 경로가 있다(2026-08-25 실측 확인).**

**🔴 세 번째 경로 — 클라우드 계정 → 로그아웃 → 게스트 진입.**

①이 막는 것은 **게스트 → 로그아웃 → 재진입** 한 방향뿐이다. 반대 방향은 열려 있다: 구글/Apple 로만
써 온 기기가 게스트로 들어가면 vault(SecureStore)에 익명 refresh token 이 없으므로 `loginAsGuest`
가 `signInAnonymously()` 로 **새 익명 계정**을 만들고, 서버는 `auth.users.created_at < 24h` 만
보므로 300 을 준다.

재설치와 달리 **대가가 0 이다.** 클라우드 단어장은 서버에 그대로 있고 재로그인하면 pull 로 돌아온다.
즉 "대가가 큰 경로만 남는다"는 위 결론이 성립하지 않는다.

실측(2026-08-25 06:36 KST): 운영자 기기에서 구글 로그아웃 후 게스트 진입 →
익명 계정 `57f096ea…` 신규 생성 → `ai_effective_plan` 이 `day_limit 300` 반환.

**파생 — 하루 100 루프.** 여기서 한 걸음 더 나가면 한도를 두 배로 쓸 수 있다.
`logout()` 이 `resetAll()` 로 `lastPulledAt` 을 0 으로 되돌리므로 재로그인은 매번 first-login
경로를 타고, `applyFirstLoginMerge()` 는 로컬 전체를 dirty 로 마킹만 하므로 **pull 과 push 가 둘 다**
돈다 — 게스트가 만든 단어는 계정으로 올라가고 클라우드 단어도 그대로 돌아온다.

```
구글 계정(클라우드 N개)
  → 로그아웃 → 게스트 진입 → 익명 계정 한도 소진 → 단어 생성
  → 구글 재로그인 → conflict → "합치기" → N + 생성분
  → 구글 계정 한도도 별도로 사용            = 하루 최대 100 (익명 50 + 클라우드 50)
```

**그럼에도 막지 않기로 했다(§7 G).** 대체재가 더 싸기 때문이다 — 보상형 광고 2회면 +40 단어를
몇십 초에 얻는다. 위 루프는 로그아웃·게스트 진입·단어 생성·재로그인·합치기 선택을 매번 거쳐야 하고,
`lastPulledAt=0` 이라 재로그인마다 **전량 pull** 을 기다린다(단어가 쌓일수록 본인이 느려진다).
관측 트리거는 §5-2.

### ②-b AI·스캔 경로의 오류·폴백 문구 【추가 2026-08-17 · 확정】

**왜 뒤늦게 붙었나.** ②의 점검 축이 "가입 유인 문구"였다. 그런데 한도가 같아지면 거짓이 되는
문장은 요금제 화면 밖에도 있다 — **오류·폴백 안내가 "세션이 없다"를 "로그인해야 한다"로
번역하고 있다.** 이 축을 빼고 착수하면 앱 문구 작업을 두 번 하게 된다.

**대상 4개 키** (ko·en·es 3 로케일).

| 키 | 지점 | 지금 문구(ko) | 왜 틀리나 |
|---|---|---|---|
| `addWord.fallbackGuest`<br>`addWord.fallbackGuestAction` | `app/add-word.tsx:376` | "무료 사전에서 가져왔어요. **로그인하면 AI가 뜻까지 채워줘요**" / "로그인하기" | 로그인해도 한도가 같아져 **거짓**. `currentGuestDesc` 와 같은 이유인데 ② 목록에 없었다 |
| `aiError.unauthorized`<br>`scanError.unauthorized` | AI 단어 생성 · 사진 스캔 | "로그인이 필요해요. 다시 로그인한 뒤 시도해주세요." | 게스트가 받으면 "로그인해야 쓸 수 있다"로 읽힌다 — §1 의 **"유도하지 않고 안내한다"** 와 정면 충돌 |

⚠️ **`fallbackGuest` 는 1.6.0 을 기다릴 것 없이 이미 어긋나 있다.** 폴백 사유의 이름은
`'guest'` 지만 실제 발생 조건은 **세션이 아예 없을 때**다(`lib/translation-api.ts:219~221`).
1.5.0 부터 게스트는 익명 세션을 가지므로 이 문구는 **게스트에게 뜨지 않는다** — 이름과 문구가
조건보다 한 세대 뒤처져 있다.

#### 확정 문구 — 원인만 말하고 행동을 시키지 않는다

```
ko  AI에 연결하지 못했어요. 잠시 후 다시 시도해 주세요.
en  Couldn't reach AI. Please try again shortly.
es  No se pudo conectar con la IA. Inténtalo de nuevo en un momento.
```

**근거.** 이 오류가 뜨는 사용자는 **이미 로그인했거나 게스트로 시작한 상태**다 —
`app/(tabs)/_layout.tsx:186` 이 `authMode === 'none'` 을 `/login` 으로 되돌려보내므로 탭 화면에
미인증 상태로 있을 수 없다. 그런데도 오류가 나는 이유는 **`authMode`(로컬 저장 의도)와
Supabase 세션이 별개**여서, 의도가 `guest` 인데 익명 세션만 만료·무효화된 경우다.
**사용자가 고칠 수 있는 일이 아니므로 행동을 시키지 않는다.**

> **기각한 안 — "시작 화면에서 로그인하거나 게스트로 시작해 주세요".**
> 로그인 강요로 읽히지 않게 게스트를 명시하는 장점이 있었으나, **그 말을 들을 상대가 없다.**
> 위 탭 가드 때문에 "아직 시작하지 않은 사용자"는 이 화면에 도달하지 못한다.

⚠️ es 는 **tú**, AI 는 **IA**(② 와 동일 규칙).
🔑 `aiError.unauthorized` 와 `scanError.unauthorized` 는 **문구가 글자 그대로 같다** —
한쪽만 고치면 어긋난다.

#### 키를 줄일 기회 — `'guest'` 폴백 사유를 합친다

확정 문구는 기존 `addWord.fallbackServer`("AI에 연결하지 못해 무료 사전에서 가져왔어요.
잠시 후 다시 시도해 주세요.")와 사실상 같은 문장이다. 따라서:

| 파일 | 지점 | 내용 |
|---|---|---|
| `lib/translation-api.ts` | `EnrichFallback` 의 `'guest'`(:24) · 발생 지점(:221) | **`'serverFailed'` 로 합친다.** 실제 조건이 "세션 없음"이고 사용자에게 할 말이 같다 |
| `app/add-word.tsx` | `fallbackNotice` 의 `'guest'` 분기(:375~377) | 분기 삭제 → `fallbackServer` 로 흡수 |
| `i18n/locales/{ko,en,es}.json` | `addWord.fallbackGuest` · `fallbackGuestAction` | **키 2개 삭제**(3 로케일 = 6줄) |

로그인 유도 링크(`router.push('/login')`)도 함께 사라져 §1 방침과 맞는다.

#### 별건 — 손대지 않는다: `common.aiApiKeyRequiredDesc`

"AI 기능을 사용하려면 Gemini API 키가 필요합니다"는 세션 없음에 **BYOK 발급**을 안내해
내용상 틀렸지만, **프로덕션에서 도달하지 않는다.**

```
canGenerateAi = hasApiKey || (authMode !== 'none' && EDGE_ENABLED)   (screen.tsx:732)
                              └ 탭 가드로 항상 참    └ 프로덕션 = 1
```

`eas env:list production` 실측 결과 `EXPO_PUBLIC_ENRICH_VIA_EDGE=1` 이므로 이 식은 **항상 참**이고
안내는 죽은 코드다. 1.6.0 문구 작업 대상이 아니며, 죽은 안내 정리로 따로 다룬다.
🔑 **주석이 "게이트를 고쳤다"고 적혀 있어도 게이트가 실제로 열려 있는지는 값을 확인할 것** —
검토 과정에서 이 줄을 두 번 잘못 읽었다(한 번은 주석을 믿어서, 한 번은 플래그를 안 재서).

- Play: 등록정보는 릴리스와 독립 → **심사 종료 후 즉시**. 🔴 심사 중에 건드리면 검토가 리셋된다.
- App Store: 설명이 **버전 메타데이터** → 1.6.0 과 함께 나간다.

### ④ 서버 — 게스트 등급을 없앤다 【확정】

대상은 `ai_effective_plan` 한 함수. 새 마이그레이션으로 `create or replace`.

**게스트를 Free 와 같게 하는 데 그치지 않고, `is_anonymous` 분기 자체를 제거한다.**

```sql
-- 지금
tier      : is_anonymous → 'guest', else 'free'
day_limit : pro 3000
          / not is_anonymous and created_at > now()-'24h' → 300
          / is_anonymous → 10
          / else 50
reward_amount    : is_anonymous 10 / else 20
reward_max_views : is_anonymous  1 / else  2

-- 1.6.0 — is_anonymous 가 한 번도 등장하지 않는다
tier      : 'pro' / 'free'
day_limit : pro 3000 / created_at > now()-'24h' → 300 / else 50
reward_amount    : 20
reward_max_views : 2
```

최종 정책은 한 문장으로 적힌다.

```
누구나  첫 24시간 300단어 → 이후 하루 50단어 (+ 광고 1회 20단어, 하루 2회까지 = 최대 90)
Pro     월 3,000단어
게스트 ↔ Free 차이 : 없음.  로그인의 의미 : 백업 · 동기화 · 기기 이동
```

**첫 24시간 300 도 게스트에게 동일하게 준다.** 실측 근거: 300 부스트 도입 후 가입 36명 중
첫날 AI 를 쓴 사람은 10명이고, 그중 **50단어를 넘긴 사람은 1명(575단어)** 이다. 90%에게는
하루 90으로 충분하고, **첫날 대량으로 쓰려는 10% 를 놓치지 않기 위해** 300 을 남긴다.
(원래 근거였던 "첫 세션 사진 스캔이 벽에 부딪힌다"는 하루 90 으로 대부분 해소되므로 약해졌다.)

**앱 영향.** `tier` 에 `'guest'` 가 오지 않으므로 게스트도 요금제 화면에 **Free** 로 표시된다.
광고 가드는 `tier === 'pro'` 만 보므로 영향 없다(`lib/ads/admob.ts`). `tierGuest`·`accountTierGuest`
같은 키는 쓰이지 않게 되면 정리한다. 내부 분석은 `auth.users.is_anonymous` 로 계속 가능하다.

**재설치 우회는 의도적으로 허용한다.** 앱을 지웠다 깔면 새 익명 계정이라 300 을 다시 받는다.
막지 않는 이유:

- 얻는 것이 **1회 약 120원어치**(AI 단어 1개 원가 ≈ 0.4원)인데, 대가는 **쌓아 둔 단어장 전체**다.
- 확실히 막으려면 기기 식별이 필요하고, 그 개발 비용이 남용 손해보다 압도적으로 크다.
- ①로 **로그아웃-재진입(3탭·손실 0)** 을 막고 나면 남는 경로는 재설치뿐이다. 대가가 큰 경로만 남는다.

대신 **관측은 한다** → §5-2.

**적용 조건: ①②③이 스토어에 도달한 뒤.** 앱 릴리스 전에 올리면 문서와 실제가 어긋난다.
**되돌리기**: 서버 값이라 즉시 가능.

### ⑤ 미사용 익명 계정 정리 — 【채택하지 않음】

Supabase 는 익명 계정의 주기적 삭제를 권장하지만 **이번에 하지 않는다.**

전제 정리 — 게스트 데이터는 두 곳에 나뉘어 있다. **단어는 기기에만 있고**(로컬 SQLite, 우리가
접근할 수 없다), 서버에는 **신원 행(`auth.users`)과 사용량 기록(`ai_usage_daily`)** 만 있다.
따라서 "정리"는 단어를 지우는 것이 아니라 서버의 빈 신원 행을 청소하는 뜻이다.

**하지 않는 이유:**

1. 🔴 **①과 충돌한다.** 서버 계정을 지우면 그 기기의 게스트는 다음 실행에서 세션이 무효가 되어
   새 계정을 만든다 → **한도가 리셋된다.** ①로 막으려던 것을 청소가 되살린다.
2. 규모상 불필요하다 — 계정 행은 매우 작고, Supabase 무료 한도는 월 50,000명인데 우리는 월 수십 명이다.
3. 지표 혼동은 `is_anonymous` 로 갈라 보면 해결된다.

⏭️ 익명 계정이 수천 단위로 쌓이면 그때 다시 검토한다. 그때도 **①을 깨지 않는 기준**(예: 세션
만료가 이미 지난 계정만)이어야 한다.

## 4. 표준 대비 — 따르지 않기로 한 것

Supabase 공식 문서와 대조한 결과, **두 가지는 의도적으로 채택하지 않는다.**

| 항목 | 공식 권장 | 채택 여부 |
|---|---|---|
| 익명→영구 계정 **링크 승격** | `updateUser`/identity 링크로 같은 `user_id` 유지 | **안 함.** 링크의 이점은 서버 데이터 이관인데 우리 게스트 데이터는 로컬이라 이관할 것이 없다. 충돌 분기만 늘어난다 |
| **captcha** | 익명 로그인 남용 방지 | **안 함.** 봇의 대량 생성을 막는 장치라, 사람이 3탭으로 리셋하는 경로를 못 막는다. 정당한 게스트에게만 마찰이 생긴다 |
| 익명 계정 정리 | 권장 | **안 함.** ①(세션 유지)과 충돌해 한도 리셋을 되살린다. 규모상 이득도 없다 → ⑤ |

## 5. 검증과 관측

### 5-1. 배포 검증

| 단계 | 방법 |
|---|---|
| ① | 실기: 게스트 진입 → AI 사용 → **로그아웃 → 재진입** → 한도가 이어지는지. 동시에 DB 에서 익명 계정이 늘지 않았는지 확인 |
| ① 회귀 | 게스트 진입 크래시 재현 시나리오(로그아웃 직후 "바로 시작하기" 즉시 탭) |
| ④ | 배포 후 `select * from ai_effective_plan('<익명 uuid>')` — `tier='free'`·`day_limit` 300/50 확인 |

### 5-2. 재설치 남용 관측 — 막지 않되 눈은 뜬다

**남용은 서버에 특징적인 흔적을 남긴다.**

```
정상 계정 : 생성 → 조금씩 사용 → 며칠에 걸쳐 활동이 이어짐
남용 계정 : 생성 → 24시간 내 300 소진 → 이후 활동 0 → 곧 새 계정 등장
```

8/13 데이터에서 실제로 관측된 모양이다(`01:40` 소진 → `01:52` 새 계정). 로그아웃 경로였지만
재설치도 같은 형태로 남는다. 여기에 `auth.sessions` 의 **IP 대역 + user_agent** 를 얹으면
정밀도가 오른다(어제 익명 14개를 운영자/실사용자로 가른 방법).

**점검**: 주 1회 수동 쿼리. 24시간 내 250단어 이상 소진 + 이후 활동 0 인 익명 계정을
IP /16 대역으로 묶어 센다. → `docs/ops-analytics-queries.md` Q12 로 추가할 것.

**트리거 — 익명 계정 하루 90단어 초과 (2026-08-25 추가).**

익명 계정이 하루에 쓸 수 있는 최대는 부스트 없이 **90** 이다(기본 50 + 보상형 광고 2회 ×20).
그러므로 **90 을 넘긴 익명 계정은 300 부스트를 실제로 소비했다는 증거**다. 세 번째 경로(§3 ①)와
하루 100 루프를 동시에 감지하는 단일 판정선이라, 이 값 하나만 본다.

```sql
-- 부스트를 실제로 태운 익명 계정. 한 건이라도 나오면 §7 G 를 재검토한다.
select a.user_id, a.usage_date, a.word_count, a.rewarded_bonus
  from public.ai_usage_daily a
  join auth.users u on u.id = a.user_id
 where u.is_anonymous and a.word_count > 90
 order by a.usage_date desc, a.word_count desc;
```

기준선(2026-08-25 실측): 30일간 익명 계정 **최고 22단어**. 판정선까지 4배 여유가 있다.
8/18 이전의 20단어 계정들은 옛 게스트 한도 10 + 광고 10 에 막힌 것이라 "안 쓴다"의 근거가 아니다 —
게스트가 300 을 받을 수 있게 된 것은 `20260818000000` 을 적용한 **8/24 부터**이고, 그 이후 표본은
익명 계정 6개·최대 10단어로 아직 판단 근거가 못 된다.

**대응 단계**

| 단계 | 관측 | 대응 | 비용 |
|---|---|---|---|
| 0 | 없음 | 그대로 | 0 |
| 1 | 위 트리거 1~2건 | **부스트 소진 표식**(B안) — `user_subscriptions.signup_boost_forfeited` + RPC `forfeit_signup_boost()`, `loginAsGuest` 가 새 익명 계정 생성 직후 신고. 신규 게스트의 300 은 지킨다 | 앱 릴리스 1회 |
| 2 | 한 대역에서 2~3건 | 300 부스트 축소·폐지(서버 값) — 표적 자체가 사라진다 | 즉시·0 |
| 3 | 계속·확산 | 기기 식별 도입 | 아래 |

⚠️ 단계 2(부스트 폐지)를 단계 1 뒤로 미뤘다(2026-08-25). **게스트에게도 첫날 300 은 준다**는
것이 확정 방침이므로, 부스트 자체를 없애는 것은 표식(B안)이 듣지 않을 때의 차선이다.

**2단계의 실제 비용**(참고 — DeviceCheck 는 과하다):

| 플랫폼 | 수단 | 재설치 후 유지 | 비용 |
|---|---|---|---|
| Android | `ANDROID_ID`(`expo-application`) | ✅ 거의 확실 | 패키지 1개 |
| iOS | **Keychain 플래그**(`expo-secure-store`, **이미 설치됨**) | △ 대체로 유지, 기기 초기화 시 소실 | 코드 몇 줄 |

서버에 기기 해시 테이블 하나가 추가된다. iOS DeviceCheck(완벽하지만 네이티브 모듈 필요)는
"120원 아끼려고 기기를 초기화하는 사람"까지 막게 되므로 채택하지 않는다.
