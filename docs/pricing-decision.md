## 3. 진단: 문제는 가격이 아니라 **팔 물건이 없다**는 것

```
Free 한도      100 단어/일
실제 사용       25 단어/일 (활성일 중앙값)   ← 아무도 안 닿는다
```

- 보상형 광고 **요청이 30일간 단 1회**인 것이 방증이다(한도 초과 시에만 뜨므로).
- 지금 Pro가 파는 것은 "한도 100 → 1,000"이다. **존재하지 않는 불편을 파는 셈**이다.
- 과거 체험 48명 중 전환 0이 이것을 증명한다 — 그들은 Pro를 공짜로 써보고도
  **아무 차이를 못 느꼈다.** 가격을 내렸어도 결과는 같았을 것이다.

**→ 이번 개편의 본질은 가격 조정이 아니라 처음으로 팔 물건을 만드는 것이다.**

## 5. 권고안

| | Free | Pro (**₩3,900 유지**) |
|---|---|---|
| 단어 검색 | **하루 100개 그대로** | 무제한 |
| 뜻만 보기 | **언제나 무제한** (한도를 넘겨도) | — |
| **사진 스캔** | **하루 2~3회** | **무제한** |
| **AI 단어 생성** | **하루 1~2회** | **무제한** |
| 광고 | 배너 | 없음 |
| 안전장치 | **하드캡 하루 300 / 월 2,000** | — |

**한도 100을 그대로 두는 이유**: 실사용이 25개라 아무도 안 걸린다. 낮추면 하향이라
반발과 별점이 오는데 얻는 게 없다. 대중화 방향과도 맞는다.

**스캔·생성으로 경계를 긋는 이유**: 이 둘은 **눈에 보이는 기능**이다. "한도 10배"는
설명해야 알지만 사진 스캔은 써보면 안다. 경쟁 앱에 아예 없어 값을 매길 명분도 있다.
⚠️ **아예 막으면 있는 줄도 모르고, 무제한이면 살 이유가 없다** — 매일 맛은 보게 할 것.
⚠️ 스캔 2~3회·생성 1~2회라는 **숫자는 근거가 얇다**(쓰는 사람이 4명뿐이라 분포가 안 나온다).

**하드캡이 필요한 이유**: 뜻만 보기가 무제한이면 AI 호출도 무제한이 된다(§6).
한도는 더 이상 비용을 막지 못하므로 진짜 상한이 따로 있어야 한다. 실측 최대가
하루 575개·월 1,347개라 하루 300/월 2,000이면 정상 사용자는 안 걸린다.

### 가격은 지금 올리지 말 것

구독자가 1명이라 **잃을 게 없어 올리기 좋아 보이지만**, 상품 개편과 가격 인상을 같이 하면
전환 0의 원인이 가격이었는지 상품이었는지 **영영 알 수 없다.** 창은 안 닫힌다 —
Pro 50명까지는 언제든 올릴 수 있고 기존 구독자는 옛 가격을 유지시킬 수 있다.

**같은 이유로 reverse trial·광고 재설계도 2차로.**
경쟁 기준으로는 월 ₩6,900 / 연 ₩49,000이 정당하다(VoCat Pro ₩7,900보다 13% 저렴).

**순서**: 1차 = 스캔·생성 제한 + 뜻만 표시 + 하드캡 → 2차(Pro 10명쯤) = 가격·체험 → 3차 = 광고.

## 6. 한도 초과 시 "뜻만 표시" 설계

한도를 넘긴 Free 사용자가 새 단어를 검색하면 **지금은 빈손으로 돌아간다**(광고 모달만 뜬다).
대신 **AI를 전부 호출해 캐시에 저장하고, 화면에는 뜻만 보여준다.**

**이 방향이 옳은 이유**(경량 프롬프트안을 대체한다 — §12):
- 서버는 **이미** 풀 결과를 전역 캐시에 저장 중이라 **구현 비용이 0**이다
  (`enrich_cache`는 `user_id`가 없는 공유 테이블)
- 뜻만 *생성*하면 그 단어를 Pro가 열 때 캐시 미스 → 풀 호출이 추가되어 **오히려 비싸다**(₩0.42)
- Pro 전환 시 **소급이 공짜**다 — 전체가 이미 캐시에 있으므로 "지금까지 모은 87개 단어가
  바로 완성됩니다"가 원가 ₩0인 판매 문구가 된다

⚠️ **"뜻만 보여주면 DB가 빨리 쌓인다"는 인과는 성립하지 않는다.** 축적 속도는 AI 호출 횟수가
정하고 표시 정책과 무관하다. 표시 제한은 **판매 설계**이지 축적 수단이 아니다.

### 확정된 동작 규칙

| | |
|---|---|
| 저장 | 사용자 DB에는 **뜻만**. CSV는 `list.words`에서 나가므로 **자동 해결**(`csv-file.ts:47`) |
| 차감 | **서버에 갔으면 차감, 폰 안에서 끝나면 무차감.** 뜻만 받는 것은 **무차감·무제한** |
| 미완성 단어 복구 | **수동.** 경로가 이미 있다 — `WordDetailModal.tsx:468` 편집 모드의 AI 자동완성 버튼.<br>자동 복구는 사용자가 손으로 쓴 예문을 덮어쓴다 |

### 🔴 저장소가 세 개다 — 이걸 놓치면 잠금이 뚫린다

| | 위치 | 니모닉 등 전체 |
|---|---|---|
| ① 서버 캐시 | `enrich_cache` | 있음 (전역 공유) |
| ② **기기 캐시** | AsyncStorage `@soksok_enrich_*` | 있음 |
| ③ 사용자 DB | SQLite + `cloud_words` | 뜻만 저장할 예정 |

`translation-api.ts:85`가 **②를 먼저 보고 한도를 쳐다보지 않는다.** 그래서 한도 초과로 뜻만 본
단어를 **곧바로 다시 검색하면 ②가 히트해 전체가 나온다.** → ②에 **"잘린 결과" 표시**가 필요하다.
그래야 한도가 회복됐을 때 ①에서 공짜로 전체를 복구할 수 있다.

### 예문 학습이 몰래 AI를 부른다

`features/study/examples/screen.tsx:152` `startBackgroundEnrich` — 예문 없는 단어를
**동시 3개씩·최대 3회 재시도**로 자동 보강한다. 뜻만 저장이 정책이 되면 예문 없는 단어가
*정상*이 되어 **사용자가 아무 버튼도 안 눌렀는데 대량 차감**된다.

**폐지도 검토했으나 "자동 채우기만 제거"를 권한다**:
- 재료는 충분(예문 보유율 97.7%)하고 **주 무대인 큐레이션 덱은 100% 예문 보유라 영향이 없다**
- 최근 2주 최다 투자 기능(7/26 빈칸 로직+테스트19, 7/29 실기통과, 8/3 P7·P8)이자 경쟁 우위 항목
- 자동 채우기 제거는 오히려 복잡도(동시성·backoff·Abort)를 통째로 줄인다

⚠️ **학습 모드별 실사용은 측정 자체가 불가능하다** — 서버에 기록이 없다(`cloud_study_days`는
날짜·개수만). 기능 존폐를 판단할 근거가 없다는 것 자체가 문제다.

## 7. 캐시 시딩 — 사용자를 기다리지 말 것

### "언젠가 Vertex 비용이 0이 되나?"

**0은 안 된다**(Heaps 법칙상 새 단어는 계속 생긴다). **그러나 총액이 무의미하게 작다:**

| 사전 전체를 미리 만들면 | en→ko만 | 주요 5개 언어쌍 |
|---|---|---|
| 실용 어휘 2만 | **₩8,000** | ₩40,000 |
| 오타·고유명사까지 5만 | ₩20,000 | ₩100,000 |

개발 투입 ₩1,270만의 **0.3%**, 고정비 한 달 치보다 싸다.
→ **AI 원가는 통제 대상이 아니라 이미 끝난 문제다.** 원가를 이유로 Free를 조이는 설계는 근거가 없다.

### 규모별 비용 (현행 ₩0.4 기준 / 10월 이후 ₩1.2)

| 시나리오 | 호출 | 지금 | 10월 이후 |
|---|---|---|---|
| 덱 단어 그대로 재생성 | 10,479 | ₩4,192 | ₩12,575 |
| **덱 단어 × 5개 도착어** | 52,395 | **₩20,958** | ₩62,874 |
| 주력 4쌍만 (en↔ko, en↔es) | 11,162 | ₩4,465 | ₩13,394 |
| 사전급 — 출발어당 1만 × 30쌍 | 300,000 | ₩120,000 | ₩360,000 |

소요 시간: 분당 300건이면 5만 건 2.9시간, 30만 건 17시간.

### 저작권

- **Google 약관은 문제없다.** 무료·유료 모두 출력물 소유권을 주장하지 않고 상업 사용을 허용한다.
- **새로운 위험도 아니다.** 앱은 **지금도** AI 생성 뜻·예문을 제공 중이다. 미리 만드느냐
  검색할 때 만드느냐는 법적으로 같다.
- ⚠️ **이 DB는 해자가 아니다** — AI 생성물은 저작권 보호가 어렵고 경쟁자도 같은 값에 만들 수 있다.
  주는 것은 원가와 속도이지 독점이 아니다.

### 단어 목록

**`hermitdave/FrequencyWords`**(GitHub, OpenSubtitles 기반 61개 언어, **CC BY-SA 4.0**)가
6개 언어를 한 번에 덮는다. 보조로 영어 NGSL(이미 사용 중), 중국어 HSK, 한국어 국립국어원.
**일본어 JLPT는 공식 목록이 비공개, 베트남어는 표준 목록이 없다.**

⚠️ **자막 기반이라 그대로 쓰면 안 된다** — 감탄사·비속어·고유명사·오타가 상위에 섞인다.
`isReal` 판정 + 문자 체계 필터 + 품사 필터가 필요하고, **목록을 구하는 것보다 이쪽이 손이 많이 간다.**

⚠️ **단어 목록에도 권리가 붙을 수 있다.** 개별 단어는 저작물이 아니지만, ① 선택·배열에 창작성이
있으면 **편집저작물**(저작권법 제6조), ② 창작성이 없어도 상당한 투자에 대해 **데이터베이스제작자의
권리**(제4장의2, 5년)가 인정된다. 다만 우리 용도는 **재배포가 아니라 생성 대상 지정**이고,
`enrich_cache`는 `(term, source, target)` 키라 **배열이 승계되지 않으므로** 위험이 낮다.
그래도 공개 라이선스 목록을 쓰고 출처를 표기하면 논쟁 자체가 안 생긴다(NGSL에 이미 하는 방식).

### 시딩 전 선결 조건 — ✅ 2026-08-09 모두 해소

1. ✅ **`PROMPT_VERSION` v7 확정·배포** — 니모닉 제거 + 예문 표제어 강제. L1 캐시 키에도 버전을
   넣어 이제 bump가 기존 기기까지 닿는다. 🔴 **구조는 그대로다** — `enrich_cache` PK에 버전 축이
   없어 bump = 전량 무효. **시딩 후에는 사실상 못 올린다.**
2. ✅ **`isReal=false` 캐시 쓰기 버그 수정**(§10 ①) — 오염 212건 삭제 완료.
3. ✅ **품질 확인 수단** — `scripts/seed-cache.ts`에 내장했다. 판정에는 앱이 실제로 쓰는
   `canBlankExample`을 그대로 import 한다(복제하면 앱과 어긋나도 모른다).

## 9. 니모닉 — 접기로 결정

`mnemonic`은 AI가 매번 생성해 캐시에 저장하지만 **화면에 닿는 경로가 없다**:
`.tsx` 전체에 출현 0회, `Word` 타입(`lib/types.ts:5`)에 필드가 없어 **저장 시 버려진다**.
`cloud_words`에도 컬럼이 없다. §4 기능표에 "우리만 있음"으로 적혀 있었으나 **사실이 아니었다.**

### 품질 실측 (무작위 30개 분류)

- **쓸 만한 것 약 1/3** — 형태·소리를 쪼개 뜻과 연결한 경우
  (`eternity` → "이 **터널**은 끝이 없어 보여", `masterpiece` → "마스터가 만든 피스")
- **무의미 약 2/3** — 이미 외래어로 아는 단어를 반복하거나 순환
  (`artist` → "아, 정말 artist 같아!", `buy` → "바이어(buyer)는 물건을 사러 온다")
- **해로운 것도 있다** — `fragment` → "**fragrant**는 향기로운 조각이다" (다른 단어와 혼동)
- **같은 언어(ko→ko, en→en)에서는 논리적으로 성립하지 않는다** — `눈` → "눈으로 본 것을 기억하자"

### 개선은 가능하지만 값이 맞지 않는다

프롬프트를 예시 중심으로 고치면 **3.5-flash-lite에서는 훌륭하게 작동한다**(비움 10/15,
같은 언어 3/3, 어원 오류 소멸). **그러나 현행·3.1에서는 작동하지 않는다** — "좋은 연상이
없으면 비워라"는 판정 기준이 주관적이라 유독 어려운 지시다.

즉 **니모닉 품질을 얻으려면 모델을 3.5로 올려야 하고, 그러면 모든 원가가 4.4배가 된다.**

| | 시딩 52,395건 | 니모닉 |
|---|---|---|
| 지금 2.5-flash-lite로 | **₩20,958** | 품질 안 나옴 |
| 3.5-flash-lite로 | ₩92,215 | 잘 나옴 |
| **차액 = 니모닉의 진짜 값** | **₩71,257** + 운영 원가 4.4배 | |

**"한 줄"의 값어치를 한참 넘는다. → v7 프롬프트에서 제거한다**(출력 토큰도 줄어 원가가 내려간다).

### 접는 다른 이유들

- **원조인 Memrise가 2021년에 "mems"를 완전히 제거했다.** 사용자 요청이 계속 있지만 되돌리지 않았다.
- 잘 되는 곳(메모리워드, 일 사용자 10만)은 **이미지 연상**으로 한다 — 텍스트 한 줄과 다른 물건이다.
- 표시하려면 `Word` 타입 + SQLite 마이그레이션 + `cloud_words` 컬럼 + 동기화 + 매퍼 + UI + 설정
  토글이 필요하다. **얻는 게 "절반쯤 쓸 만한 한 줄"인데 치르는 게 DB 마이그레이션이다.**
- **"뜨문뜨문"이 구조적 문제다** — 좋은 것만 남기려 엄격히 걸수록 빈칸이 늘어난다.
  있다 없다 하면 기능이 아니라 버그로 보인다.

## 10. 🐛 코드 버그 — ✅ 2026-08-08~09 모두 수정

### ① Edge가 `isReal=false`도 캐시에 썼다 — ✅ 수정·배포·정리 완료

클라이언트는 `isReal === false`면 캐시하지 않는데(`lib/translation-api.ts:114`)
Edge에만 그 규칙이 빠져 있었다(`enrich-word/index.ts`, 커밋 `94a16eb`).

오염 212건(전체의 8.3%)을 삭제했다. 확인해 보니 **대부분 개발 중 테스트 흔적**이었다 —
출발어를 `vi`로 둔 채 넣은 한국어 문장 94건, 제품 라벨 스캔 30건, 터미널 화면 스캔 7건.
**모델의 진짜 오판은 사실상 없었다**(판정 능력은 믿어도 된다는 뜻). 사진 스캔에 찍혀
term 키로 남아 있던 **타인 이메일 1건**도 함께 사라졌다.

⚠️ 남은 구조적 문제: 사진에 찍힌 임의 문자열이 전 사용자 공용 테이블의 키가 되는 경로는
그대로다. 지금은 1건뿐이라 급하지 않으나 유입이 늘기 전에 볼 것.

함께 고친 것 — `upsert` 실패는 throw 가 아니라 `{ error }`로 오는데 `try/catch`로 감싸고
있어 **캐시 쓰기 실패가 로그조차 안 남고 있었다.**

### ② 로컬 캐시에 `prompt_version`이 없었다 — ✅ 수정(다음 앱 빌드에 실림)

`lib/enrich-cache.ts`의 키에 버전을 넣었다(커밋 `a6ba0ba`). 이게 없으면 L1이 버전과
무관하게 옛 결과를 반환하고, L1이 L2보다 먼저 걸려 **프롬프트를 고쳐도 이미 그 단어를
조회한 기기에는 영영 닿지 않았다.**

옛 키는 고아로 남기고 지우지 않는다 — 정리하려면 앱 시작 시 AsyncStorage 전 키 스캔이
필요해, 콜드 스타트를 늘리는 값이 아낀 수백 바이트보다 비싸다.

⚠️ **앱 빌드 전까지는 BYOK 사용자와 "이미 조회한 단어"가 v6 그대로다.**

## 11. 운영 주의

### PROMPT_VERSION bump = 캐시 전량 무효화 = 비용 스파이크

`enrich_cache` PK는 `(source_lang, target_lang, term)`이라 버전이 키에 없다.
조회는 버전으로 필터하므로 **버전을 올리면 전체가 한꺼번에 미스가 되고 전부 재생성된다.**

현재 **v7**(2026-08-09 배포). **사소한 문구 수정으로 버전을 올리지 말 것.**

⚠️ v6 캐시 2,027건은 **아직 지우지 말 것** — 사용자 폰에 깔린 앱이 여전히 v6으로 조회한다.
다음 앱 빌드가 나간 뒤에 정리한다.
**시딩 후에는 사실상 못 올린다**(§7 선결 조건 1).

⚠️ 프롬프트는 **두 곳에 복제**되어 있다 — `_shared/gemini-vertex.ts`(Edge)와
`lib/ai/gemini-client.ts`(BYOK). `PROMPT_VERSION`(`enrich-word/index.ts:40`)과
`SHARED_ENRICH_PROMPT_VERSION`(`lib/enrich-cache-shared.ts`)도 함께 올려야 한다.

### 캐시 히트는 quota를 차감하지 않는다 → 차감으로 바꾸기로 합의

캐시가 쌓일수록 Free가 사실상 무제한이 되어 **우리가 캐시를 열심히 쌓을수록 Pro를 팔 수 없게 되는
구조**다. quota의 역할이 "비용 상한"에서 "제품 티어 구분"으로 바뀌므로 차감이 맞다.
부작용은 없다 — L1이 먼저 걸리므로 **이미 본 단어를 다시 여는 것은 차감되지 않는다.**

### 캐시 히트율이 낮은 이유는 유입 부재다

히트 상위 단어(open·start·action·appear·leave)는 전부 기초 영단어로, **흔한 단어는 이미 잘 쌓여 있다.**
기존 사용자는 L1에 있어 L2까지 안 오고, 신규 사용자가 없다. **유입이 늘면 히트율이 함께 오른다.**

## 12. 재측정 방법

### AI 원가

```sql
select date_trunc('month', usage_date)::date as 월,
       sum(word_count) as 총단어, sum(call_count) as 총호출,
       round(sum(word_count)::numeric / nullif(sum(call_count),0), 2) as 호출당단어,
       count(distinct user_id) as 사용자수
from ai_usage_daily group by 1 order by 1 desc;
```

`호출당단어`가 튀는 달은 `generate`(1호출=20단어)·`scan-image` 비중이 높았던 달이다.
**호출당 5 이상인 날 = 스캔·생성을 쓴 날**로 간주할 수 있다.

### 하루 소비 분포 (한도 설계용 — 활성일 기준으로 볼 것)

```sql
select percentile_disc(0.5) within group (order by word_count) as 중앙값,
       percentile_disc(0.9) within group (order by word_count) as p90,
       max(word_count) as 최대
from ai_usage_daily where word_count > 0;
```

### 캐시 재사용률 (히트 카운터가 아니라 조회/고유로 볼 것)

```sql
select count(*) as 고유단어, sum(hit_count) as 누적히트,
       count(*) filter (where hit_count = 0) as 재조회0
from enrich_cache;
```

> ⚠️ `sum(hit_count)`는 **Edge 경로 히트만** 센다. BYOK(`fetchSharedEnrich`)는 카운터를
> 올리지 않고, L1이 반복 조회를 먼저 흡수하므로 **실제 재조회율의 하한**이다.

### 사용자 간 단어 중복 (시딩 효과 예측)

```sql
-- ⚠️ 큐레이션 덱을 반드시 제외할 것. 포함하면 69.6%로 부풀려진다(덱 복사분).
select count(*) filter (where users >= 2) * 100.0 / count(*) as pct_2plus
from (select lower(trim(cw.term)) t, count(distinct cw.user_id) users
      from cloud_words cw join cloud_lists cl on cl.id = cw.list_id
      where cw.is_deleted is not true and cl.is_curated is not true
      group by 1) x;
```
