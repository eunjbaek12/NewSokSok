## P3 — 단어 저장 시점 background enrich 큐

**무엇:** 단어 저장 시 빈 예문이면 background 큐에 적재 → 학습 시점에 이미 채워져 있음.

**왜 보류:**
- 빈 예문 단어가 *어디서* 들어오는지 측정 안 됨. 추측 기반 큐 설계는 잘못된 추상화 위험.
- 현재(P0+P1)는 빈 예문이 있어도 학습을 막지 않아 사용자 차단 효과 없음.

**트리거 (이 중 하나 발생 시 진행):**
- 사용자 피드백에 "예문이 없다"가 반복 등장
- 큐레이션 import 후 빈 예문 비율이 높다는 게 측정됨
- examples 학습 진입 시 background enrich 배너가 너무 자주 뜬다는 불편 제기

**선행 작업:**
- 빈 예문 진입점 측정 (add-word 스킵 / 큐레이션 / generate-words / 사진 스캔 중 어디)
- 진입점이 한 곳이면 큐 대신 그 흐름 안에서 일괄 enrich로 충분

**예상 작업량:** 진입점 측정 후 큐 + 재시도 + UI 상태까지 며칠.

## P4 — Batch enrich Edge Function

**무엇:** 1 콜에 N단어 묶어 enrich. `supabase/functions/generate-words` 인프라(`_shared/gemini-vertex.ts` + rate-limit + quota RPC) 재사용 가능.

**왜 보류:**
- 출시 직후 DAU=0 시점엔 비용·quota 최적화 의미 없음.
- Gemini N단어 배열 출력의 안정성 리스크(잘림/누락) — chunk size, retry, fallback 등 검증 비용 큼.
- Edge function 신규 배포 + 배포 시 회귀 리스크.

**트리거 (이 중 하나 발생 시 진행):**
- DAU 100+ 도달 + Free tier quota 압박 누적
- 운영자 GCP/Vertex 토큰 비용이 의미 있는 수준 (월 몇 만원+)
- 사진 스캔 활성화로 enrich 트래픽 폭증

**구현 메모:**
- chunk size 5~10 권장 (Gemini 출력 안정성)
- quota 정책 재정의 필요 (단어당 1 차감 유지 / 또는 chunk 단위 할인)
- BYOK 경로도 batch로 호출 가능 (사용자 quota 절약)
- 새 EnrichMode `'batch'` 추가 또는 별도 endpoint `enrich-words-batch`

**예상 작업량:** 1~2일 (Edge 구현 + 프롬프트 + 검증).

## P5 — 콜드 스타트 직후 첫 enrich 일시 실패의 "조용한 빈 결과" → 재시도 안내

**무엇:** 앱 콜드 스타트 직후 첫 enrich가 stale/미준비 세션 토큰으로 Edge `unauthorized`(refresh-retry 1회도 실패) 또는 Vertex 일시 오류로 떨어지면, `autoFillWord`가 조용히 사전 fallback으로 빠진다. en source면 영어 정의/예문만 채워지고 **번역 뜻(meaningKr)은 빈값** → 사용자는 "왜 뜻이 안 나오지?"만 보고 원인을 모른다. 앱 재시작하면 세션이 새로 hydrate되어 정상화.

→ AI 경로가 `unauthorized`/`upstream_failure`로 실패할 때 빈 결과를 그대로 반환하는 대신 **"AI 일시 오류 — 다시 시도" 안내 + 재시도 버튼**을 노출하거나, 첫 enrich 전에 세션 준비를 보장(보강 호출 전 `getSession` await + 필요 시 1회 refresh)한다.

**왜 보류:**
- 자가 치유됨(재시작/재시도 시 정상). 데이터 손상 없음 — 빈 뜻은 캐시도 안 됨(`setCachedEnrich`가 meaningKr 가드).
- 출시 차단 사안 아님. 빈도·체감 신호 측정 전 과설계 위험.

**트리거 (이 중 하나 발생 시 진행):**
- 사용자 피드백에 "뜻이 안 나온다/가끔 빈다"가 반복 등장
- 콜드 스타트 첫 enrich 실패율이 측정상 유의미

**구현 메모:**
- 사전 fallback과 "AI 실패"를 호출자가 구분할 수 있게 신호 분리(현재는 둘 다 빈 결과로 합쳐짐).
- en source의 사전 fallback은 *정상 동작*이므로(영어 정의 제공), AI 실패와 구분해 fallback 자체는 유지하되 "뜻 미생성" 사유만 표시.

**관찰:** 2026-06-09 TestFlight build 9, en→zh 단어 검색에서 첫 시도 뜻 빈값 → 앱 재시작 후 정상. zh 전용 문제 아님(코드상 en→zh는 BYOK·Edge 모두 완전 지원).

**예상 작업량:** 반나절 (신호 분리 + UI 분기 + 세션 prewarm).

## P6 — 예문이 표제어를 아예 포함하지 않는 경우 (생성 품질)

**무엇:** `pnpm run diagnose:examples` 실측(2026-07-29, 표본 4000) 중 발견. 출제 제외 사례
대부분은 예상된 활용형 미스매치(`쉽다`→"쉬워요", `걷다`→"걸어요", `vivir`→"vivo")인데,
**일부는 예문에 표제어가 어떤 형태로도 등장하지 않는다**:

- `올리다` :: "그는 자신의 연구 논문을 저명한 학술지에 성공적으로 **게재하여** 학계의 주목을…"
- `遣る` :: "彼は日夜を問わず、研究室に籠もり、ひたすら難解な数式と格闘しておった。"

빈칸 로직이 못 찾는 게 아니라 **찾을 대상이 없다.** 즉 `lib/example-blank.ts`의 한계로
확정하고 덮은 "잔여 2.4%"([[project_example_blank_matching]]의 "측정 후 안 고치기로 확정")와는
**원인이 다른 별개 건**이다. 그쪽은 사전이 필요한 형태소 문제, 이쪽은 AI 생성 프롬프트 문제다.

**왜 보류:**
- 사용자 피해가 없다 — 해당 카드는 예문 학습에서 조용히 빠질 뿐, 정답이 노출되지는 않는다.
- 전체 비중이 작고(출제 제외 자체가 ko 2.8%·cjk 5.1%, 그중 일부), 프롬프트 수정은
  `PROMPT_VERSION` bump + 3곳 동기화 + Edge 재배포 + 캐시 재생성까지 파급이 크다.

**트리거:**
- 예문 학습에서 "이 단어는 왜 안 나오냐"는 피드백
- 진단 스크립트에서 출제 제외율이 기준선(ko 2.8 / latin 0.5 / cjk 6.4) 대비 유의하게 상승

**구현 메모:**
- 프롬프트에 "예문은 표제어를 **그대로 또는 활용형으로 반드시 포함**" 지시 추가.
- 서버에서 생성 직후 `segmentExample`로 자체 검증해 미포함이면 1회 재생성하는 쪽이 더 확실
  (프롬프트 지시만으로는 flash-lite가 종종 어긴다). 단 비용·지연 증가.
- 기존 저장분은 캐시에 남으므로 소급 적용하려면 재생성이 필요하다.

**예상 작업량:** 프롬프트만이면 반나절(+ Edge 재배포·회귀 E2E), 서버 검증까지면 1일.

## P7 — 스피커가 빈칸의 정답을 그대로 읽어버린다 🔴

**무엇:** `features/study/examples/screen.tsx:542`

```
text={stripSenseMarkers(currentWord.exampleEn)}   // 원문 전체
```

화면은 `HighlightedSentence`가 표제어 자리를 빈칸으로 파는데(`showTerm=false`),
**TTS에는 그 처리가 전혀 걸려 있지 않다.** 정답 공개 전에도 원문을 통째로 읽으므로
스피커를 한 번 누르면 정답이 귀로 나오고, 문제가 성립하지 않는다.

**⚠️ 이건 한 번 "의도된 동작"으로 판정된 적이 있다 — 그 판단이 뒤집혔다.**
2026-07-26 예문학습 검토에서 이 동작을 발견하고도 **"자발적 힌트로 판단해 그대로 둠"**
으로 결론냈다([[project_example_blank_matching]]의 "안 하기로 확정" 목록에 그렇게 적혀 있다).
2026-07-29 preview 실기에서 은정님이 **"스피커를 클릭해서 읽게 하면 결국 답이 다 나온다"**
고 지적해 뒤집혔다. **되돌리지 말 것** — 옛 결정을 근거로 "의도된 동작"이라 판단하면 안 된다.

**왜 뒤집혔나:** "자발적 힌트"라는 전제가 틀렸다. 사용자가 답을 보려고 누르는 게 아니라
**발음을 들으려고** 누르는 버튼이다. 학습 의도대로 눌렀는데 문제가 무력화되므로,
자발적 선택이 아니라 함정에 가깝다.

**결정이 필요하다 — 코드가 작다고 바로 짜지 말 것.** 후보:
1. 빈칸 구간을 **묵음으로 건너뛰고** 앞뒤만 읽는다 (문장 리듬이 깨진다)
2. 정답 공개 전에는 **스피커를 감춘다** (가장 단순하지만 발음 학습 기회를 잃는다)
3. 빈칸을 "**블랭크**" 같은 말로 치환해 읽는다 (Anki·교재 받아쓰기 관행)
4. 정답 공개 후에만 전체 문장, 공개 전엔 1·3 중 하나

`segmentExample`이 이미 빈칸 구간을 알고 있으므로(`lib/example-blank.ts`) 세그먼트를
재조립하면 1·3은 어렵지 않다. **어느 쪽이 학습에 나은지가 진짜 질문이다.**

**구현 메모:** `SpeakerButton`은 7곳 공용이므로([[project_tts_speaker_hardening]])
읽을 문자열을 **호출부에서 만들어 넘기고** 컴포넌트는 건드리지 말 것.

**예상 작업량:** 결정 후 반나절(+ 실기).

## P8 — 힌트가 빈칸 안에 들어가서 잘린다

**무엇:** 빈칸을 누르면 뜻이 **빈칸 박스 안에** 렌더된다(`screen.tsx:61`,
`{showHint ? meaning : '?'}`). 그런데 그 박스는 `<Text>` 안에 놓인 **인라인 `View`**라
줄바꿈되지 않는다 — 한 덩어리로 취급돼 문장 줄에 끼어들고, 뜻이 길면 폭을 넘겨 잘린다.
`blankBox`에 `maxWidth`가 없고 `blankText`에 `numberOfLines`도 없다.
동음이의어면 `meaning`이 "①… ②…" 조립본이라([[project_homonym_meanings]]) 훨씬 길다.

**왜 지금이 아닌가:** 잘려도 앞부분은 보이므로 힌트 역할은 부분적으로 한다.
그리고 고치는 방향이 P7의 결정과 얽힌다 — 힌트를 빈칸 밖(문장 아래 줄)으로 빼면
빈칸은 순수하게 "가려진 자리"로 남아 P7의 1·3안과 자연스럽게 맞물린다.

**구현 메모:**
- 인라인 View의 폭 제약은 RN에서 잘 안 듣는다. **힌트를 문장 아래 별도 줄로 빼는 쪽**이
  구조적으로 맞다(빈칸은 `?` 유지, 아래에 "뜻: …" 한 줄).
- 그 경우 `minWidth: showHint ? 60 : 40` 분기와 `hintBg`/`hintBorder`/`hintText` 토큰의
  쓰임이 바뀐다 — 토큰을 지우지 말고 아래 줄로 옮길 것.
- 레이아웃이 한 줄 늘어나므로 `a252ed2`가 확보한 세로 여유를 다시 계산해야 한다
  (780dp 화면·하단 예약 124dp 기준. 3버튼 내비바 `insets.bottom`=58dp).

**예상 작업량:** P7과 함께 반나절~1일(+ 실기).
