# 병기 예문 쪼개기 (예문 학습) — 스펙

작성 2026-08-21. 상태: **구현 완료 · 실기 미검증.** 결과는 12장.

동음이의어 병기(①②③)로 저장된 단어가 예문 학습에서 **한 카드에 문장 2~3개 + 빈칸
2~3개**로 나오는 것을 고친다. 카드가 쓰는 예문·뜻·번역·낭독을 **번호 하나짜리 세트**로
좁힌다. 앱 안에서만 처리하고 **덱 데이터·서버는 건드리지 않는다.**

[[example-choices-multi-answer-spec]] 작업 중에 발견해 별건으로 분리한 것이다.

---

## 1. 원칙

> **문항 하나는 뜻 하나를 묻는다.**

지금은 뜻 두세 개와 문장 두세 개를 함께 보여주면서 **어느 뜻을 묻는지 알려주지 않는다.**
길이 문제로 발견했지만 본질은 출제 정확도 문제다.

## 2. 현재 상태 (2026-08-21 실측, 서버 `official_words` 15,542행)

- 서버 예문의 **32.8%(5,101개)** 가 ①②③ 병기다. 2문장 3,137개 · 3문장 1,966개.
- 덱별 편차가 크다: 수능 필수 어휘 500 **57%** · 기초 영어 필수 1000 56% · TOPIK I 350 16.6%.
- `segmentExample` 은 표제어가 나오는 **자리마다 전부 빈칸을 뚫는다**(`lib/example-blank.ts`
  의 ranges 가 복수) → 병기 예문은 빈칸이 2~3개가 된다.

**뜻·예문·번역이 번호로 완전히 대응한다** — 이것이 쪼갤 수 있는 근거다:

```
term       goods
meaningKr  ① 상품, 물품                    ② 식료품
definition ① Items that are bought...      ② Food and drink...
exampleEn  ① The store sells a wide...     ② The market was stocked...
exampleKr  ① 그 가게는 다양한...            ② 시장은 신선한...
```

병기 5,101개 중 네 필드의 번호 집합이 일치하는 것이 **5,099개(99.96%)**.

## 3. 왜 쪼개도 안전한가 — 커버리지 손실이 0이다

각 문장에 `canBlankExample` 을 돌려 본 결과:

| | 값 |
|---|---|
| 모든 문장에서 빈칸 가능 | 4,946 (97.0%) |
| 일부 문장만 가능 | 128 (2.5%) |
| 어느 문장도 불가 | 27 (0.5%) |
| **통짜(현행)로 빈칸 가능** | **5,074 (99.5%)** |

"빈칸을 만들 수 있는 문장 중에서 고른다"는 규칙이면 97.0 + 2.5 = **99.5%** 로 통짜와
정확히 같다. 못 쓰는 27개는 통짜로도 이미 출제에서 빠지는 것들이다(스페인어 활용형
`tener → Tengo`, 일본어 표기 차이 `取りあえず → とりあえず`).

⚠️ 단순 `includes(term)` 으로 재면 "일부만 20.3%" 라는 과대추정이 나온다 — `monopoly`
의 ② `We played Monopoly` 처럼 대소문자·굴절이 다른 경우를 놓치기 때문이다. **판정은
반드시 `canBlankExample` 로 한다.**

## 4. 개선폭

| | 지금 | 쪼갠 뒤 |
|---|---|---|
| 예문 길이 | 중앙 63자 · p90 **159자** · 최대 257자 | 중앙 26자 · p90 60자 · 최대 143자 |
| 힌트(뜻) 길이 | 중앙 31자 · p90 70자 · 최대 **207자** | 중앙 10자 · p90 29자 · 최대 128자 |
| 빈칸 수 | 2~3개 | 1개 |
| 출제 가능 | 99.5% | **99.5%** |

힌트 줄은 `numberOfLines={2}` 로 잘린다(`screen.tsx`). p90 70자가 29자로 내려가면
잘림이 사실상 사라진다.

🔴 **잘림 위험은 실재한다.** 카드는 `minHeight: CARD_MIN_HEIGHT` + **`flexShrink: 1`**
이고 **ScrollView 가 없다.** 스타일 주석에 "모자라면 카드부터 줄어든다"고 적혀 있는데,
카드가 줄면 안의 텍스트가 잘린다.

## 5. 설계

### 5.1 카드가 보는 출처를 하나로 좁힌다

```
currentWord (저장된 그대로 · 병기 텍스트)
      │
      │  splitSenseText() 로 번호별 분해 → 하나 선택
      ▼
senseView  ← 문장·힌트·번역·낭독이 모두 이것만 본다
```

### 5.2 선택 규칙

```
1. exampleEn 을 번호로 쪼갠다                     번호가 없으면 → 통짜 (현행)
2. 쪼갠 문장 중 canBlankExample 이 true 인 것만 후보
3. 후보 중 무작위 하나                             ← 결정 (6장)
4. meaningKr · exampleKr 에서 같은 번호를 꺼낸다    없으면 → 그 필드만 통짜
5. 후보가 하나도 없으면 전부 통짜 (현행 동작으로 복귀)
```

### 5.3 카드가 떠 있는 동안 고정, 다시 만나면 새로 뽑는다

단어 id 별 선택을 `useRef` 맵에 캐시한다 — `choicesMapRef` 와 **같은 패턴**이다.
리렌더로 뜻이 바뀌지 않고, 세션이 끝나면 리셋되므로 다음에 그 단어를 만나면 다른 뜻이
나온다. 6장의 결정을 실제로 구현하는 지점이 여기다.

## 6. 결정 (2026-08-21)

| 항목 | 결정 | 근거 |
|---|---|---|
| **어느 번호를 쓸까** | **카드마다 무작위**(세션 안에서 고정) | "항상 ①"은 단순하지만 **②③ 뜻이 예문 학습에 영영 안 나온다** — 뜻을 여러 개 만들어 넣은 이유가 여러 뜻을 가르치려는 것인데 나머지가 화면에 도달하지 못하면 죽은 데이터가 된다 |

## 7. 🔴 함정

- **번호 개수가 필드마다 다를 수 있다.** 실측 2건(`伸ばす`·`抜ける`)이 `definition` 에
  번호가 중복으로 박혀 있다(`①②③②②③`). **번호는 예문 기준으로만 세고**, 다른 필드는
  같은 인덱스가 없으면 그 필드만 통짜로 둔다.
- **출제 목록 필터는 통짜 기준인데 여기는 안 바꾼다**(`screen.tsx` 의 `ready` 필터).
  쪼갠 후보가 없을 때 통짜로 폴백하므로 목록의 판정과 카드의 판정이 어긋나지 않는다.
  바꾸면 두 곳이 따로 놀 위험이 생긴다.
- **`shouldShowExampleTranslation` 도 senseView 기준으로 호출한다.** 통짜끼리 비교하면
  번역 표시 여부가 실제로 보여줄 문장과 다르게 판정된다.
- **큐레이션 전용이 아니다.** add-word 에서 뜻을 여러 개 고른 사용자 단어도 같은 병기
  텍스트라 그대로 적용된다.
- **낭독·힌트·번역이 전부 senseView 를 봐야 한다.** 화면은 가리고 소리는 안 가려서
  정답이 새어 나갔던 P7 과 같은 실수를 반복하지 않기 위해서다.

## 8. 범위 밖

- **플래시카드 · 단어 상세 · 퀴즈.** 뜻을 여럿 아는 것이 목적인 화면이라 병기 전체가 맞다.
- **정답 공개 후 다른 뜻 보여주기.** 고른 세트만 유지한다 — 다른 뜻은 단어 상세에서 본다.
- **데이터 · 서버 · 마이그레이션.**

## 10. 테스트

```
S  "① A ② B"              → ["A", "B"]
S  번호 없는 텍스트         → null (호출부가 통짜로 분기)
S  "① A ② B ③ C ④ D"      → 4개
S  번호 앞 머리말 · 빈 항목 → 버린다
S  중복 번호(伸ばす 형태)   → 예문 기준 개수를 넘지 않는다
V  빈칸 가능한 문장만 후보가 된다
V  후보가 없으면 통짜를 돌려준다
V  같은 카드에서 두 번 호출해도 같은 세트 (세션 캐시)
```
